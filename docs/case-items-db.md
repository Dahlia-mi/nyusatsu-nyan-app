# 案件品目DB

## 位置付け

`案件品目DB`は、正式登録済み案件の複数品目を管理するSSOTである。

- `案件マスター`: 案件IDと案件ヘッダーの親テーブル
- `案件品目DB`: 案件IDに属する複数品目の正本
- `case.json`: OCR・CSV・手入力の共通入力形式、および登録時点の互換スナップショット
- `01_案件管理`: 既存Web・見積処理向けの案件ヘッダーと先頭品目の互換投影
- `03_見積書`: 見積作成用の作業台。品目の正本にはしない

## 列

| 列 | 用途 |
|---|---|
| 案件ID | `案件マスター`への参照 |
| 品目ID | 案件内で不変の品目識別子 |
| 品目名 | 品目の名称 |
| 仕様・型番 | 規格、材質、型番など |
| 数量 | 調達数量 |
| 単位 | 個、枚、式など |
| 表示順 | 案件内の表示順 |
| 有効フラグ | 履歴参照を壊さず削除を表現する |
| 作成日時 | 初回登録日時 |
| 更新日時 | 内容の最終更新日時 |
| 更新元 | 案件カルテなどの更新経路 |

単価、見積金額、仕入先ID、採用状態は品目そのものの属性ではないため、このDBには保存しない。

## 品目ID

形式は次のとおり。

```text
<案件ID>-<3桁連番>

例:
2026-07-015-001
```

案件IDは正式登録後に不変であり、品目IDも一度発行したら変更しない。UUIDより短く、人が確認しやすく、CSVや外部APIでも案件との関係を追跡しやすい。

同じ案件の同期では、次の順で既存IDを維持する。

1. 入力JSONに含まれる品目ID
2. 品目名・仕様・数量・単位の正規化一致
3. 完全スナップショット更新時のみ表示順
4. 一致しない場合は案件内の次番号を発行

発番とupsertは`ScriptLock`内で行う。

## 同期方法

新規案件登録では、`items[]`を完全スナップショットとして同期する。既存行に存在して新しい`items[]`に存在しない品目は、物理削除せず`有効フラグ=FALSE`にする。

既存案件へ別の取得元を追加する場合、入力が部分情報である可能性がある。この場合は内容一致した品目だけを統合し、未記載品目は無効化しない。位置だけを根拠に既存品目を上書きしない。

同期後の全有効品目と発行済み品目IDを`case.json`へスナップショットとして保存し、既存処理との互換性を維持する。`01_案件管理`への先頭品目投影も当面維持する。

## 既存データの移行方針

このPRでは移行処理を実装しない。移行は次の独立工程で行う。

1. 案件フォルダの`03_JSON/case.json`を案件ID単位で読み取る
2. `items[]`がある案件を移行候補として一覧化する
3. JSONがない案件は`01_案件管理`の先頭品目を候補として扱う
4. 同一案件内の表記揺れと重複候補をレポートする
5. dry-run結果をレビューする
6. 承認済み案件だけ`案件品目DB`へupsertする
7. 件数、品目ID、元データを照合してから運用を切り替える

既存JSONや`01_案件管理`を移行処理から削除・上書きしない。

## 将来拡張

- 仕入先にゃん、業者見積DBは`案件ID × 品目ID`で参照する
- 品目別利益・落札分析は品目IDを集計キーにする
- 市場カテゴリ、AI埋め込み、外部分類コードは別マスターまたは派生データとして管理する
- CSVの更新時は既存品目IDを含め、未指定時だけ照合・発番する
- 検索高速化が必要になった場合は、案件IDと品目IDのメモリ索引を読取処理内で構築する

Google SheetsにはDBインデックス機能がないため、現段階では物理的な索引列を増やさず、ヘッダー名参照と一括読取で対応する。
