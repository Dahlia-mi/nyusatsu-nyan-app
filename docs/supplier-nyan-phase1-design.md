# 仕入先にゃん Phase1 設計書

## 1. 文書情報

- ステータス: Phase1 正式設計
- 対象リポジトリ: `Dahlia-mi/nyusatsu-nyan-app`
- 基点ブランチ: `main`
- 基点コミット: `6e5d9463a65b8b996eb6163e3d9c93c0f84ff875`
- 対象範囲: 独立版「仕入先にゃん」のPhase1

本書をPhase1実装の正本とする。仕様変更は本書を更新し、レビュー後に実装へ反映する。

## 2. 目的

瑞希さんがスマートフォンから、対象案件に対する仕入先調査を止めずに進められるWebアプリを構築する。

Phase1で扱う業務は次のとおり。

1. 調査対象案件の確認
2. 既存仕入先の検索と案件への紐付け
3. 新規仕入先の登録
4. 問い合わせ状況の更新
5. 回答状況、見積金額、納期、備考の入力
6. 仕入先調査マスターへの保存

入札にゃんOSへの反映は、翠さんが内容を確認した後、既存の「仕入先調査を取り込む」機能から手動で実行する。

## 3. Phase1の対象外

次はPhase1に含めない。

- 仕入先にゃんから`業者見積DB`への直接書き込み
- 採用業者の決定
- 採用フラグ、採用原価、想定利益、利益率の更新
- 入札状態の変更
- 見積書生成
- PDFまたは画像のアップロード
- 複数回の見積履歴管理
- 品目単位の分割見積
- 入札にゃんOSの既存本体ファイルの変更
- 過去データの自動一括移行

PDF・画像アップロードはPhase1.5以降、見積履歴と品目別管理はPhase2以降で検討する。

## 4. システム境界

```text
仕入先にゃん
別Apps Scriptプロジェクト・別デプロイURL
  │
  ├─ 読取: 入札にゃんOS「01_案件管理」
  ├─ 読取: 仕入先調査マスター
  └─ 書込: 仕入先調査マスターのみ
                 │
                 ▼
       翠さんによる既存の手動同期
                 │
                 ▼
        入札にゃんOS「業者見積DB」
```

仕入先にゃんは、入札にゃんOSの次のデータを変更しない。

- `業者見積DB`
- 採用フラグ
- 採用原価
- 原価確定状態
- 適用税率
- 想定利益
- 利益率
- 案件状態
- 見積書生成情報

## 5. プロジェクト分離

同一GitHubリポジトリ内で管理するが、Apps Scriptプロジェクトとデプロイは完全に分離する。

```text
nyusatsu-nyan-app/
├─ 既存の入札にゃんOSファイル
├─ supplier-nyan/
│  └─ 独立Apps Scriptプロジェクト
├─ docs/
└─ tests/
```

本番入札にゃんOSと共有しないもの:

- Apps Scriptの`scriptId`
- デプロイID
- WebアプリURL
- Apps Scriptバージョン
- Script Properties
- テスト用スプレッドシート

## 6. 環境構成

次の3環境を分離する。

```text
仕入先にゃん テスト用Apps Script
仕入先調査マスター テストコピー
入札にゃんOS テストコピー
```

本番接続はテスト完了後に行う。

環境固有値はコードへ直接記述せず、Script Propertiesで管理する。

| キー | 内容 |
|---|---|
| `ENVIRONMENT` | `test`または`production` |
| `NYUSATSU_SPREADSHEET_ID` | 読取元となる入札にゃんOS |
| `SUPPLIER_RESEARCH_SPREADSHEET_ID` | 読み書き対象の仕入先調査マスター |
| `ALLOWED_USERS` | 許可ユーザー。カンマ区切り等の形式は実装時に固定 |
| `APP_USER_KEY_HASH` | 補助的な利用者キーのハッシュ |

`ENVIRONMENT`が未設定または許可値以外の場合、書き込みAPIは安全側で拒否する。

独立アプリでは`SpreadsheetApp.getActiveSpreadsheet()`を使用しない。対象スプレッドシートは必ずScript PropertiesからIDを取得し、`SpreadsheetApp.openById()`で明示的に開く。

## 7. 利用者と権限

Phase1の利用者は次の2名とする。

| 利用者 | 権限 |
|---|---|
| 瑞希さん | 仕入先登録、案件への紐付け、問い合わせ状況、回答状況、見積金額の更新 |
| 翠さん | 全件閲覧、登録、修正、管理 |

Phase1では複雑なロール管理を実装しない。将来の利用者追加に備え、認可処理は画面や個別APIへ分散させず共通ガードへ集約する。

### 7.1 公開範囲

- 匿名アクセスを許可しない
- Googleアカウントへのログインを必須とする
- 対象スプレッドシートの共有権限を第一の防御線とする
- 利用者メールを取得できる環境では`ALLOWED_USERS`も検証する
- 個人Gmailでメールを取得できない場合に備え、利用者キーを補助的に使用できる構成とする

瑞希さんのGoogleアカウントが個人GmailかGoogle Workspaceかは実装開始前に確認する。メールアドレス取得だけに依存する設計にはしない。

### 7.2 OAuthスコープ

独立アプリでは必要最小限のスコープを使用する。Phase1では原則としてGoogle Sheetsの読み書きに必要な範囲に限定し、Drive・Docsスコープは追加しない。

## 8. 案件データ

### 8.1 取得元

案件データは、Script Propertiesの`NYUSATSU_SPREADSHEET_ID`で指定したスプレッドシート内の`01_案件管理`から読み取る。

主な参照列:

```text
案件ID
案件名
発注機関
想定入札額(税抜)
納品期限
状態
```

列番号は固定せず、1行目のヘッダー名から解決する。

### 8.2 表示条件

次をすべて満たす案件のみ、進行中クエストとして表示する。

```text
状態が「検討中」または「見積中」
かつ
仕入先調査対象として指定されている
```

入札にゃんOSへPhase1専用列を追加しないため、仕入先調査マスターへ`調査対象案件`シートを追加する。

列案:

```text
案件ID
対象フラグ
登録日時
登録者
備考
```

状態が進行中から外れた対象案件は「完了クエスト」として表示する。対象フラグがない案件は表示しない。

## 9. 仕入先ID

Phase1で`仕入先ID`を新設し、仕入先の同一性の正本とする。会社名は表示属性であり、同一性判定の正本にしない。

形式:

```text
SUP-000001
```

発番手順:

1. `LockService`で排他制御する
2. 会社マスター内の既存最大番号を確認する
3. 次番号を発行する
4. 重複がないことを再確認して保存する

会社名を変更しても仕入先IDは変更しない。

案件別仕入先管理におけるPhase1の一意キー:

```text
案件ID × 仕入先ID
```

同じ組み合わせが存在する場合は新規行を追加せず、既存行を更新する。

入札にゃんOSの現行同期キーは、既存機能を壊さないためPhase1では変更しない。

```text
現行:
案件ID × 案件カテゴリ × 会社名

将来:
案件ID × 仕入先ID
```

同期キーの移行は、仕入先IDの運用実績を確認した後の別Phaseとする。

## 11. 既存データへの仕入先ID付与

会社名の完全一致または正規化一致を利用して、会社マスターと案件別仕入先管理を照合する。

結果を次の3区分で報告する。

```text
自動紐付け
新規会社候補
要確認
```

次のデータは自動確定しない。

- 同じ会社名が会社マスターに複数存在する
- 表記揺れ候補が複数存在する
- 案件別仕入先管理にしか存在しない会社
- 会社名が空欄

バックフィルは独立した移行工程とし、アプリ実装コミットへ混在させない。

## 12. 会社登録・案件紐付け

### 12.1 既存会社

```text
会社マスターを検索
→ 会社を選択
→ 案件別仕入先管理へ案件との紐付けを登録
```

会社マスターの既存行は、案件への紐付けだけでは更新しない。

### 12.2 新規会社

```text
会社情報を入力
→ 仕入先IDを発行
→ 会社マスターへ登録
→ 案件別仕入先管理へ案件との紐付けを登録
```

会社マスター登録と案件紐付けの途中失敗を考慮し、再実行時に重複登録されない設計とする。

### 13.2 回答あり

```text

```

### 13.3 見積取得済み

```text
見積取得 = TRUE

```

日付は自動入力後に手動修正できる。

すでに日付が設定されている場合、状態ボタンの再押下だけでは上書きしない。ユーザーが日付欄を明示的に変更して保存した場合のみ更新する。

## 17. API共通ルール

- 返却形式は`{ success, data, error }`に統一する
- 書き込みAPIは`LockService`で排他制御する
- 列番号を固定せずヘッダー名から解決する
- 必須ヘッダー不足時は書き込み前に停止する
- 対象案件IDが`01_案件管理`に存在することを確認する
- `案件ID × 仕入先ID`の重複を作らない
- クライアントから渡された行番号を正本にしない
- エラーメッセージへスプレッドシートIDや内部例外を露出しない
- 二重送信に対して冪等に処理する

- 主要ボタンの高さを44px以上にする
- 1カラム中心のレイアウトとする
- 主要操作で横スクロールを発生させない

## 21. テスト計画

### 21.1 設定・権限

- Script Properties不足時に書き込みを拒否する
- 未許可ユーザーを拒否する
- 匿名ユーザーが利用できない
- `test`と`production`のIDが分離される
- 権限不足時に分かりやすいエラーを表示する

### 21.2 案件取得

- `検討中`、`見積中`かつ調査対象の案件だけ表示する
- 他状態の案件を進行中へ表示しない
- 調査対象外の案件を表示しない
- 必須ヘッダー不足時に安全に停止する

### 21.3 会社・仕入先ID

- 新規会社へ一意な仕入先IDを発行する
- 同時登録でも仕入先IDが重複しない
- 会社名変更後も仕入先IDを維持する
- 既存会社を検索して案件へ紐付けできる
- 同じ案件ID・仕入先IDを2回登録しても重複しない

### 21.4 調査情報

- 問い合わせ済み操作で問い合わせ日を自動入力する
- 回答あり操作で回答日を自動入力する
- 自動入力した日付を修正できる
- 状態ボタン再押下で既存日付を意図せず上書きしない
- 見積金額、納期、備考を保存できる
- 不正な金額を拒否する

### 21.5 監査

- 新規登録時に作成日時と更新日時を記録する
- 更新時に作成日時を維持する
- 更新者と更新元を記録する

### 21.6 入札にゃんOSとの境界

- 仕入先にゃんから`業者見積DB`へ書き込まない
- 採用状態、原価、利益を変更しない
- 既存の手動同期で追加、変更なし、更新が成立する
- 同期後の税・送料確認制限が維持される
- 採用済み見積が再同期で保護される

### 21.7 UI

- スマートフォン幅で横スクロールが発生しない
- 主要操作が片手で実行できる
- 保存中表示が分かる
- エラーと警告が画面内で読める
- 二重タップで重複登録されない
